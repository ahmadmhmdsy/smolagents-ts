## Layers

Four layers, each with a stable seam:

1. **Model adapters.** `AbstractModel` (`pydantic_ai_slim/pydantic_ai/models/_abstract.py:18-99`)
   fixes the identity surface; `Model` (`models/__init__.py:524`) adds the request pipeline, profile
   merge, settings clamping and context lifecycle. Each provider module in `providers/` owns client
   construction, auth and error mapping; each model class owns message translation and wire shape.
2. **Graph runtime.** `pydantic_graph` supplies typed nodes, fork and join paths, and a `GraphRun`
   (`pydantic_graph/pydantic_graph/graph_builder.py:153,425`). The agent loop is one graph: nodes
   `UserPromptNode` (`_agent_graph.py:646`), `ModelRequestNode` (`:1439`), `CallToolsNode`
   (`:2364`), `SetFinalResult` (`:2875`), all sharing `GraphAgentState` and `GraphAgentDeps`
   (`:379-503`).
3. **Agent and capability layer.** `Agent` (`agent/__init__.py:593`) assembles model, instructions,
   toolsets, output type and capabilities, then converts them into a run's dependency object.
   `AbstractCapability` (`capabilities/abstract.py:179`) is the public extension point: roughly
   sixty lifecycle hooks from `before_run` (`:721`) through `on_output_process_error` (`:1383`),
   plus the declarative accessors for instructions, model settings, tools, model choice and workspace.
4. **Plumbing.** Messages, usage, retries, deferred calls, settings and the event stream are plain
   data types in their own modules. Durable execution wraps layer 1 and the tool layer in engine
   operations (`durable_exec/_base.py:287`); evaluation wraps a whole run from the outside
   (`pydantic_evals/pydantic_evals/dataset.py:276`).

## Core abstractions

**Model request contract.** A request is not "messages plus options". It is a `ModelRequestParameters`
object (`models/__init__.py:206-312`) carrying function tool definitions, native tools, the output
mode, output object schema, output tool definitions, the prompted-output template, text and image
permission flags, structured instruction parts, thinking and cache settings. Adapters consume this,
so a model's capabilities are described once and applied by the adapter rather than re-derived at
each call site.

**Profiles as capability facts.** `ModelProfile` (`profiles/__init__.py:55-120`) is a typed dict of
optional booleans and thresholds: `supports_tools`, `supports_json_schema_output`,
`supports_json_object_output`, `supports_image_output`, `supports_inline_system_prompts`, cache and
thinking facts, context window. Merged from defaults, provider, model family and user override, it
answers "can this model do X" without `isinstance` checks or provider-name branching.

**Toolsets.** `AbstractToolset` (`toolsets/abstract.py:85-160`) is a lifecycle object, not a list:
`for_run`, `for_run_step`, `__aenter__`/`__aexit__`, `get_tools`, `get_instructions`, `call_tool`,
`get_tool_for_tool_def`. `ToolsetTool` (`:51-82`) binds a tool definition to its arg validator,
retry limit and callable. Composition happens through wrappers: combined, filtered, prefixed,
prepared, renamed, metadata, approval, deferred loading, return schemas, dynamic.

**Output schema.** `OutputSchema` (`_output.py:443`) is built once from `output_type` and converts a
model response into a typed value or a retry. Subclasses cover tool output, native, prompted, text,
image, structured text and unions; `OutputToolset` (`_output.py:1496-1632`) presents output tools to
the model as a toolset.

**Run context.** `RunContext` (`_run_context.py:177`) is the per-run, per-step handle passed to tools,
validators, hooks and instructions: deps, model, usage, limits, deadline, message history,
validation context, retry counters, tool identity, approval state, partial-output flag, run and
conversation ids, metadata, model settings, capability and workspace state.

**Durable execution.** `BaseDurabilityCapability` (`durable_exec/_base.py:287-419`) is an
`AbstractCapability` that routes model requests and wrapped tool calls through engine-specific
durable operations. Engine packages subclass it and supply a `DurableOperationBackend`; the base
owns cache identity, naming, model reconstruction and workspace routing.

## One run, end to end

1. `Agent.run`/`iter` resolves the effective spec, overrides and run options, then builds
   `GraphAgentDeps` and `GraphAgentState` (`_agent_graph.py:379-503`). The state survives the whole
   graph: history, usage, output retries used, step counter, ids, metadata, pending messages.
2. `UserPromptNode` (`:646`) decides the next step from the history shape. A fresh prompt builds a
   request; a history ending in tool calls goes straight to execution; a history ending in a
   provider-suspended response resumes it; a history with an unprocessed call and a new prompt is a
   `UserError` rather than a silent repair.
3. Before a request, dynamic toolsets are rebuilt for the step (`ToolManager.for_run_step`), and
   instructions are assembled from the agent, capabilities and toolsets into ordered parts.
4. `_prepare_request_parameters` (`:996-1077`) emits `ModelRequestParameters`: tool definitions
   split into function and output tools, resolved native tools, output mode, output schema object,
   prompted template, and instruction parts. Deferred-capability and revealed-tool state is folded
   in here, which is why the observed request matches what the model receives.
5. `ModelRequestNode` (`:1439`) lets capabilities rewrite the request (`before_model_request`,
   `wrap_model_request`, `after_model_request`), then calls the model.
6. The model class prepares messages and parameters against its profile, hands them to the provider
   adapter, and returns a `ModelResponse` of typed parts. A stream is exposed as
   `StreamedResponse` (`models/__init__.py:1433`) and consumed into
   `CompletedStreamedResponse` (`:1744`).
7. Stream chunks become `AgentStreamEvent`s. The graph drains its event buffer (`_agent_graph.py:413`)
   into the run's event stream, so a UI or a durable engine sees the same events as an ordinary run.
8. `CallToolsNode` (`:2364`) validates every tool call before executing anything
   (`ToolManager.validate_tool_call` returns `ValidatedToolCall`, `tool_manager.py:161-199`), then
   executes function tools and output tools under one of three end strategies documented at
   `_agent_graph.py:145-172`: early, graceful, exhaustive, with per-tool `sequential` acting as a
   barrier.
9. An output tool call that validates ends the run through `SetFinalResult`. A validation failure
   becomes a `RetryPromptPart` in the history and costs one unit of the output-retry budget
   (`consume_output_retry`, `:450-467`).
10. A tool that raises `ModelRetry` is retried by re-prompting the model, not by re-running the
    function; the retry count lives on the tool and the manager, not in the function wrapper.
11. Hooks fire around validation and execution (`before_tool_validate`, `wrap_tool_execute`, and
    their error counterparts), which is where approval, deferral and instrumentation attach.
12. `FinalResult` is converted into `AgentRunResult` (see `result.py`, imported at
    `durable_exec/temporal/_durability.py:41`), then `after_run` and `wrap_run` hooks close the run.
13. A durable engine has replaced steps 6 and 8 with journaled operations: the model request and
    each wrapped tool call become durable units whose results replay from a journal, and the model
    object is rebuilt from a string id on the far side of the boundary.
14. Evaluation sits outside: a task function runs the agent, evaluators score an
    `EvaluatorContext`, and a report aggregates cases, scores, labels and metrics.

## State and persistence

- **Run state is explicit.** `GraphAgentState` holds message history, `RunUsage`, output retries
  used, `run_step`, `run_id`, `conversation_id`, metadata, the event buffer and a per-run MCP tool
  definition cache. Nothing relies on module globals for in-run state.
- **History is the durable record.** Message parts are the API contract with the provider, and
  resume decisions read the tail of history rather than a separate checkpoint. Suspended responses
  are persisted with a state marker, and resuming means re-issuing the turn with the provider.
- **Two different persistence stories.** A durable engine keeps one in-flight run alive by
  journaling model and tool calls (`durable_execution/overview.md:7`). Snapshotting settled steps so
  a run can be saved, resumed or forked later is a separate harness capability
  (`durable_execution/overview.md:9-10`), which the documentation explicitly contrasts with
  durability.
- **Identity.** `run_id` is per run and never inherited from history; `conversation_id` is inherited
  from the last message when present. Both are UUID7 strings, so ordering is time-based and a
  resume can name a conversation without inventing a session store.

## Streaming and transport

Streaming is an adapter capability, not a separate code path: `request_stream` is an async context
manager on the model, and `CompletedStreamedResponse` can be produced from either a streamed or a
non-streamed request. The agent consumes stream events to emit partial output, validate partial
structured data and publish UI events. Two consequences are visible in the source:

- partial structured output is validated with a trailing-strings tolerant parse, so a partially
  emitted JSON string does not fail the run (`_output.py:973-990`);
- a streaming request that fails before its first event falls back like a failed open, while a
  failure after the first event propagates (`models/fallback.py:348-370`).

Transport is delegated. Provider modules own HTTP clients and auth; retrying transports are an
optional integration, and the retry documentation separates transport, provider-SDK, fallback,
tool and output retries as distinct layers with independent budgets (`retries.md:9-25`).

## Build, test and docs

- `uv` workspace, Python 3.11 to 3.15 in the make targets (`Makefile:16-22`).
- `make format` and `make lint` run Ruff (`Makefile:28-36`); `make typecheck` runs Pyright
  (`Makefile:66`); `make test` runs pytest without coverage (`Makefile:72`); `make all` chains
  format, lint, typecheck and the coverage run (`Makefile:120`).
- Tests use recorded provider traffic and inline snapshots; documentation examples are executed by
  `tests/test_examples.py`, and `tests/test_docs_parity.py` compares page and README copies.
- CI is a GitHub Actions workflow (`.github/workflows/ci.yml`); the README badges name CI, PyPI and
  supported Python versions (`README.md:3-6`).
- Documentation routes are owned by `navigation.yml`; the repository contributor guide requires
  examples in pages to be runnable and provider-specific behaviour to live on provider pages.

The agent loop, output pipeline, toolset layer, capability hook surface, durable-execution base and
evaluation data model were read closely enough to trace an end-to-end path. The graph library was
read at class level, not at path-resolution level. Provider adapters, the harness, the terminal
client and the UI adapters were not traced, so claims about them elsewhere in this folder are
