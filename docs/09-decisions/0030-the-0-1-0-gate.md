# 0030 — 0.1.0 publishes after the pre-release set, with a stated gate

**Contract**
- **Role:** one decision, with its context and consequences.
- **Mutability:** frozen once accepted. A later change is recorded in a new file that supersedes this one; the text below stays as accepted.
- **Read when:** preparing the first release, or asking what 0.1.0 contains and what must be true before it is published.
- **Update when:** never. A reversal is a new record.

- **Status:** accepted
- **Date:** 2026-10-25
- **Decided by:** owner, answering `D-05` in the open-decisions plan
- **Supersedes:** none; it complements `0024`, which fixed the ordering after the correction pass, by fixing the release bar and the scope of the first version

## Context

`T-14` was blocked on registry credentials, and the release runbook had never been executed. I verified the tree and the registry before asking for the gate rather than trusting the row: all eleven manifests read `0.1.0`, no changesets are pending, both the `@smolagents-ts` scope and the unscoped `smolagents-ts` name are still unclaimed on the registry (both answered `E404`), no npm credential exists on this machine (`npm whoami` answers `ENEEDAUTH`), and the runbook's own first line says every step is a hypothesis until the first run.

Two decided rows change what a consumer would see if they landed after a publish: `D-01` changes the `.run()` contract and the public `RunState` type, and `D-02` changes planning behaviour. Everything else left on the register is additive -- a parity scenario, a docs page, an example, a hardening batch, a retrieval phase. `0024` already argued that the first published surface must not carry behaviour the project has decided is wrong; this record applies that argument to the remaining decisions and states the bar.

## Decision

0.1.0 publishes once the pre-release set is implemented and the gate below is satisfied. The publication itself stays with the owner's credentials; this record fixes the bar and the scope, not the date.

**Scope.** 0.1.0 contains the six-phase program plus the pre-release decisions: `D-01` and `D-02`, and `D-06` if that row is decided pre-release. Rows decided post-release ship in a later version and do not delay this one.

**Gate.**

1. `D-01` and `D-02` implemented, tested and documented -- both change public behaviour, one changes a public type.
2. Any further row decided pre-release is included; the post-release rows are explicitly out.
3. `D-03` and `D-04` landed -- done before this record.
4. `pnpm gate` green on the exact release revision, `main == origin/main`, and CI green on the same revision; a local gate is not a CI run.
5. The `@smolagents-ts` scope and the unscoped name are owned by the publishing account, and a token that can publish without an interactive OTP sits in the operator's `~/.npmrc`.
6. The release note exists before the publish: a GitHub Release on the facade tag whose body carries the scope line (0.1.0 is the six-phase program) and the install line. The root `CHANGELOG.md` belongs to the context pack, so the release note is the only user-facing place for "what 0.1.0 is".
7. Post-publish verification runs exactly as the runbook has it: `npm view` on every name, then a fresh directory that has never seen this repository installs the facade and imports it.

**Runbook amendments folded into the release** (all pre-publish, all recorded in the runbook):

- **Step 3's expected output is corrected.** Observed on 2026-10-25: the applied-bump state prints an empty "Packages to be bumped:" list, not the exit-1 message the runbook had predicted from an earlier state. A first operator must not read the healthy state as a failure.
- **The token class and the partial-publish recovery are stated.** The failure table gains `EOTP` (a token without 2FA bypass) and the recovery rule: re-run `pnpm changeset publish`, which skips versions already on the registry, verify every name with `npm view`, and never bump mid-recovery.
- **A release-note step is added** after the tag push, with the scope line.
- **The scope-ownership precondition becomes a checklist step** with its commands (`npm whoami`, the org claim), because the scope is unclaimed today.

## Alternatives considered

| Alternative | Why it was not chosen |
|---|---|
| Publish after the post-release rows land | Delays installable value for additive work, keeps the repository unreleased, and re-opens the "is it ready?" question with more changes to re-verify; that is the risk `0024` was written to avoid. |
| Publish a prerelease under a dist-tag first | The runbook refuses it without a record; it consumes the same immutability rules and adds a release path that is never removed. |
| Publish as soon as credentials exist, before `D-01`/`D-02` | The first install would carry a `RunState` value and a `.run()` contract the project has already decided to replace, which is the defect `0024` removed from the correction pass. |

## Consequences

**Positive**

- The first public surface is the settled one: the type, the endings and planning behave as documented on day one.
- The release path is exercised once on a coherent tree, so its output becomes the reference for every later release.
- The gate can be checked rather than argued, and each item has an owner or a command.

**Negative / accepted costs**

- Installable value waits for `D-01` and `D-02`; that is days, not weeks, but it is a wait.
- The release depends on an external input nobody in the repository controls: registry credentials and the scope claim.
- A pre-release inclusion of `D-06` would add its small surface to the same gate; that is decided by `D-06`, not by this record.

## Reversibility

The gate is reversible by a new record. The publish itself is not: npm refuses to unpublish after 72 hours, and the fixed version group means a partial release cannot be repaired one package at a time. That asymmetry is why the bar is stated before the action.
