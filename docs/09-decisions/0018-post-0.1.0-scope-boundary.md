# 0018 — the post-0.1.0 roadmap takes the production gaps, and the platform gaps stay non-goals

## Context

The competitor scan recorded in the related research lists eighteen
capabilities this port lacks. They are not one kind of thing. Some compose with
the port's existing seams and a team hits them within a week of real use —
multi-agent delegation, resumable runs behind a human approval, traces and
evals, cross-run session memory, guardrails and a schema-bound final answer.
Others are whole products that would each pull a library away from being a
library — a vector/RAG layer, a dev UI, a streaming UI transport, multimodal and
voice, an agent-to-agent protocol, MCP *server* authoring, and a workspace
sandbox. If both kinds are left "open", every future session re-litigates the
boundary, and the pull toward a platform is the one this project has already
declared against.

## Decision

The post-0.1.0 roadmap closes six **production gaps** — multi-agent, durable
runs + human-in-the-loop, tracing + evals, persistent sessions, guardrails +
structured output, and provider router / local runtimes — and every other
capability in the research stays a **non-goal** until a user asks for it and a
seam can host it without special-casing the loop.

## Alternatives considered

| Alternative | Why it was not chosen |
|---|---|
| **A — build toward parity with the fullest neighbour (LangChain.js breadth)** | Breadth is what makes those packages large and their core un-isomorphic. It trades the port's one differentiator for a race it cannot win. |
| **B — stay exactly at upstream `smolagents` parity** | Faithful, but it leaves the capabilities a team assumes on day one unbuilt, so adoption stalls at the demo. |
| **C — take the six production gaps, refuse the platform gaps** (chosen) | Keeps the library shape and the isomorphism, and answers the needs users raise first. |
| **D — decide per-request, no standing boundary** | Re-opens the same argument every session and drifts toward a platform by accretion. |

## Consequences

**Positive**

- A clear line: a proposed feature either extends a seam and composes, or it is a
  platform candidate and waits for a user.
- Each in-scope phase is additive behind an existing seam, so the core stays
  provider- and host-agnostic.

**Negative / accepted costs**

- Some users will ask for RAG, a Studio or voice and be told no for now.
- Multi-agent, resume and tracing imply new stored state and new serialization
  formats, which are this project's to keep stable once published.

## Reversibility

Easy for the boundary (a new record moves a capability in or out) and moderate
for anything already shipped, because a landed seam with no published dependents
is removed in one package until the first release.
