# S1.5 — the parity harness Implementation Plan

## Contract

- **Role:** the implementation plan for milestone S1.5 of
  `docs/design/2026-10-12-smolagents-ts-v1-design.md`.
- **Mutability:** once execution starts the steps below are frozen: a step that
  turned out wrong gets a note under the task that owns it, and the step's own
  text is not rewritten. Measured results are appended at the end.
- **Read when:** executing S1.5, or reviewing what S1.5 was supposed to deliver.
- **Update when:** a task's measured result differs from its prediction, or a
  task is added or dropped.

**Goal:** a differential harness that runs one shared scenario corpus through
two independent implementations — the installed upstream `smolagents` 1.14.0 in
Python and our `CodeAgent` in TypeScript — and fails the gate when their
normalized traces disagree on structure: the step kinds and their count, the
position of the code-execution call, each step's error presence, the
final-answer value, and the roles of the messages each side called its model
with.

**Architecture:** one corpus, two readers, one comparison.

- The corpus is one JSON file per scenario under `scripts/parity/scenarios/`: the
  task text, the scripted turns, the declared tools, the planning interval, the
  step budget, and the expectation. The slugs are `one-step-final`,
  `two-step-compute`, `no-code-block`, `error-recovery` and `step-budget`.
- The Python leg is the recorder in `scripts/parity/`. It subclasses upstream's
  `Model` and overrides `__call__` to return the scenario's next turn, so the
  upstream run is deterministic, offline and credential-free (F1). It replays
  every scenario through the installed `smolagents` 1.14.0 and writes one
  normalized trace per scenario under `scripts/parity/recordings/`, wrapped in
  metadata that names the upstream version, the interpreter version and the
  recording time (F8).
- The TypeScript leg is `packages/core/test/parity.test.ts`. It replays the same
  corpus through `CodeAgent` with `MockModel` and `ScriptedExecutor`, normalizes
  its own run the same way, reads the committed recordings with `node:fs`, and
  deep-compares the two traces field by field. It needs no Python, no network
  and no credential, so it runs inside the gate like any other core test.

The corpus cannot share one code body: upstream executes Python through its
interpreter while our `ScriptedExecutor` executes nothing and does not read
`final_answer(...)` out of the source at all (F3). Each turn therefore carries
the two sides' own script text and failure idiom beside a shared `intent`, and
the compared facts stay structural — no prompt text, no code source, no
observation text.

The comparison is a normalization contract, not a byte diff. Both sides map
their own vocabulary onto the canonical trace in the schema below, and every
mapping is stated rather than implied.

    {
      "scenario": "two-step-compute",
      "outcome": "final-answer",
      "finalAnswer": "sqrt is 4",
      "steps": ["action", "action"],
      "actions": [{ "toolCalls": ["code"], "error": false }],
      "modelCalls": [["system", "user"], ["system", "user", "assistant", "observation"]]
    }

Canonical vocabulary and the mappings that produce it:

| Canonical | Upstream 1.14.0 | Our loop | Why |
|---|---|---|---|
| `code` in `actions[].toolCalls` | `ActionStep.tool_calls[0].name === "python_interpreter"` | `ActionStep.codeAction !== null` | the two sides record one event on two different fields (F4) |
| `observation` role | `tool-response` | the `user` message after an assistant turn whose text starts with `Observation:` | the same position carries the same content kind (F2) |
| `assistant` role | `tool-call` folds into the assistant turn it belongs to, then consecutive duplicates collapse | the assistant turn as sent | the two sides split the assistant turn differently |
| `steps` | `memory.steps` minus `TaskStep` | the loop's steps minus `task` and `system_prompt` | only executed steps are compared; the final answer is its own field (F5) |
| `outcome` | a `FinalAnswerStep` on the stream, or a raised exception | `run.completed`, `run.maxStepsReached`, or a raised error | the terminal event, not its rendering |
| `actions[].error` | `ActionStep.error is not None` | `ActionStep.error !== undefined` | presence only: upstream reports a Python exception type we cannot reproduce (F10) |

**Tech Stack:** Python 3.13.7 with the installed upstream `smolagents` 1.14.0 and
its `importlib.metadata`; vitest 5 in the `core` project; `node:fs` for reading
the recordings; `MockModel`, `ScriptedExecutor` and `AgentSession` from
`@smolagents-ts/core`; `pnpm gate` as the finish line.

**Spec:** the design record's S1.5 row (line 963), its decision row D9 (line

the same recorded transcript through upstream …"); `docs/01-project.md`'s S1.5

location the recorder uses.

**Depends on:** S1 (the loop, memory and events), S2 (the model seam), S4 (the
code-execution seam and final-answer bridging). S3, S5 and S6 are not touched:
this plan adds no source file inside `packages/*/src`.

**Dependency order:** 0 → 1 → 2 → 3 → 4 → 5 → 6. Task 3 needs the corpus (1) and
the recordings (2); tasks 4 and 5 need the normalization contract task 3
implements; task 6 needs everything and ends with the gate.

**Task ownership:** one writer at a time. Tasks 1 and 2 own `scripts/parity/**`;
task 3 owns `packages/core/test/parity.test.ts` and `packages/core/AGENTS.md`;
task 4 owns `docs/10-runbooks/**`; task 5 owns `docs/09-decisions/**`; task 6

| F1 | Can an upstream run be offline, deterministic and credential-free? | `python .superpowers/spike_parity.py`: two scripted turns produced `ActionStep, ActionStep, FinalAnswerStep` with no network and no key | a `Model` subclass overriding `__call__` is the whole seam |

| F3 | Does a shared code body work? | a bare `final_answer('x')` script never stops our loop: our `ScriptedExecutor` does not parse it, the script runs out and `MockModel` raises `AgentGenerationError: MockModel script exhausted after 2 responses` | the corpus carries per-side text plus a shared `intent`, and the TS handler submits the final answer |
| F4 | What does each side record per action step? | upstream `ActionStep.tool_calls` is one `ToolCall(name='python_interpreter', arguments=<the code>, id='call_N')`; ours is `toolCalls: []` with the code on `codeAction` | one canonical `code` label from two different fields |
| F5 | Where does each side keep its steps? | upstream `memory.steps` is `TaskStep, ActionStep, ActionStep` (no final-answer step); ours is `task, system_prompt, action, action, final_answer` | compare action and planning steps only, and assert the final answer separately |
| F6 | What happens when the step budget runs out? | upstream (max_steps 2, three code turns) streams `ActionStep, ActionStep, ActionStep, FinalAnswerStep` and stores a third step that repeats the previous one's data; ours emits `run.maxStepsReached` and `run()` throws `AgentMaxStepsError` | a real divergence, pinned by scenario `step-budget` instead of hidden; T-18 owns it |
| F7 | When does each side plan? | upstream `planning_interval=1` streams `PlanningStep, ActionStep, PlanningStep, ActionStep, FinalAnswerStep` — a plan before each step; ours sets `snapshot.planning[0].stepIndex === 1`, planning after the first action | a real divergence; no planning scenario ships in this corpus, and T-16 owns it |
| F8 | Can the recorder name what it recorded against? | `importlib.metadata.version("smolagents")` is `1.14.0`, while the gitignored `smolagents/` clone beside the repository is 1.27.0.dev0 | the recordings pin 1.14.0 in their metadata, and a mismatch is a test failure |
| F9 | Is the Python leg runnable in CI? | `.github/workflows/context.yml` is the only workflow with `actions/setup-python` (3.12), and it runs the pack's own scripts; no lockfile here pins upstream `smolagents` | the recorder stays out of CI; its committed output is what the gate reads |
| F10 | How does a failing guest step differ? | upstream, `raise ValueError('boom')` then `final_answer('recovered')`: the first `ActionStep.error` is set with `observations` `None` and the loop recovers; ours throws the whole run out of a throwing handler (`AgentError: boom`, no result), while a returned `CodeResult` error (`{ code: "AGENT_EXECUTION", message: "boom" }`) is recorded on the step, the loop recovers, and `observations` is `"Error: boom"` | compare error presence, never the class or the text; each side needs its own failure idiom (scenario `error-recovery`) |
| F11 | Does a registered tool add a tool-call entry? | upstream `CodeAgent(tools=[get_weather], ...)` on `print(get_weather('Paris'))` lists only the `python_interpreter` call whose arguments are the whole block; the nested call appears only inside `observations`, and our step looks the same (`toolCalls: []`, code on `codeAction`) | a tools scenario could only be compared on step kinds and the presence of the tool's output, not on a tool-call list |

### Task 1: the shared scenario corpus

**Files:** the five scenario files in the File structure's first row (all new).

Schema, one file per scenario:

    {
      "id": "one-step-final",
      "task": "What is 6 times 7? Answer with final_answer.",
      "tools": [],
      "planningInterval": 0,
      "maxSteps": 3,

## Risks

| Risk | Impact | Likelihood | Mitigation |
|---|---|---|---|
| The corpus is read by two languages, so a schema change silently breaks one reader | the comparison runs against a stale half | medium | both readers validate the shape they read and fail loudly on a missing field; the test names the runbook when a recording is absent |
| A scripted execution makes the compared fields corpus-determined on our side | the harness proves less than it appears to | high | the plan and the runbook state exactly what it proves: that the upstream leg's real execution agrees with the corpus and that our loop consumes the same script in the same structural shape |
| The recordings are a frozen third-party artifact that rots | the test keeps passing while upstream moves | medium | the recording metadata pins 1.14.0 and the test asserts it; task 4's runbook is the re-record path |
| The divergences the spike found (F6, F7) are read as acceptable | a fidelity gap survives behind a green suite | medium | they are pinned by a scenario and by T-16 and T-18, never smoothed away |
| A throwing `ScriptedExecutor` handler is fatal to the whole run (F10) | an error scenario that looks right fails the suite for the wrong reason | medium | the corpus's `error` idiom is a returned `CodeResult` error, and the runbook records the trap |

## Notes

- The TypeScript leg reads the loop's steps through one cast, because
  `MultiStepAgent.memory` is protected and the public alternatives do not cover
  every outcome: `RunResult.steps` exists only on a successful run, and
  `AgentSession`'s step view carries no per-step error. The cast is confined to
  the test and is the analogous read to the recorder's `memory.steps`.
- What this harness does not prove: on our side the final-answer value, the
  scripted observation and the code text all come from the corpus, because our
  `ScriptedExecutor` consumes a declared result instead of computing one. The
  differential claim is therefore about the upstream leg's real execution and
  about our loop's structure, not about our executor's semantics — S4's QuickJS
  tests own that.
- The corpus ships no planning scenario on purpose: the two sides plan at
  different points, so one scripted turn list cannot drive both runs. F7 and
  T-16 carry the measurement instead.
- The TypeScript leg lives inside a vitest project on purpose: a loose Node
  script under `.superpowers/` cannot resolve `zod` and so cannot build one of
  our `tool()` definitions, while the repository's own projects resolve it.
- Records: decision 0007 (task 5), the S1.5 milestone row and the task rows
  (task 6), and the handoff entry (task 6). `docs/03-handoff.md` is written
  last, after the gate's numbers are known.

Our replay matched the first four field for field. The role comparison earns its keep on

### The divergence, as measured

`step-budget` came back divergent on all five compared fields rather than on the three the
plan predicted, so its expectation names all five and adds what our run must still do: end at
`max-steps` after two actions. Upstream spends a third model call, stores a third step whose
tool-call list is empty and whose error is set, and reports that turn's raw script text as the
final answer — the same F6 that T-18 owns. Planning stays out of the corpus for F7's reason,
with T-16 owning the choice.

### Deviations from this plan

1. **The corpus carries a third intent.** `final_answer('x')` alone never stops our loop,
   because our scripted executor does not interpret it, so each turn declares a shared
   `intent` plus one script per side (`py`, `ts`) rather than one script both could run.
2. **The corpus was corrected in task 3's commit, not task 1's.** The first recordings showed
   the wider `step-budget` divergence above, and that `two-step-compute`'s TypeScript turn
   called `print`, which is not our guest API; both changes ride with the suite that needed
   them.
3. **One commit followed task 2.** A review found `tools` declared and never wired on either
   side, so a tool scenario would have compared two tool-less runs and gone green; `c9f21fe`
   has both readers refuse it.
4. **The recorder writes LF.** Its first run wrote CRLF into a checkout whose
   `.gitattributes` promises LF, and git announced the conversion as it staged the files.
