# Plan — the post-0.1.0 roadmap: close the production gaps, keep the library shape

- **Status:** done
- **Owner:** owner
- **Created:** 2026-10-16
- **Authorized by:** owner, 2026-10-16

## Goal

Take this port from a faithful v1 to a run people keep for real work, by closing
the production gaps the ecosystem treats as table stakes — while staying a
library, not a platform. Each phase lands as reusable, typed package code behind
an existing or newly-declared seam, mirrored from the reference where one
exists, and pinned by a test. Nothing ships as throw-away glue.

## Why now

The v1 surface is complete against its own reference, and the competitor scan
in the related research shows that is not the same as complete against a team's
expectations: multi-agent, resumable runs, tracing, session memory and
structured output are assumed by every neighbour. The seams to host them already
exist — a managed agent is a tool, a checkpoint is a serialized step list, a
trace exporter consumes `AgentEvent`, a guardrail is a seam on the loop — so the
next phase is composition, not a rewrite. Doing it now, before the first
release hardens the API, is cheaper than doing it after.

## Non-goals

- Deployment/hosting, a managed platform, or a hosted sandbox service.
- RAG/vector stores, a dev UI/Studio, a streaming UI transport, multimodal,
  voice, A2A, MCP server authoring, and workspace sandboxing (fs/shell). These
  stay candidates in the research, revisited only when a user asks.
- Any capability that cannot land behind a seam without special-casing the loop.

## Approach

The port's shape is its constraint. Every phase must:

1. **Extend a seam, not the loop.** A new capability is declared as an extension
   point (a store, an exporter, a guardrail, an approval handler) that the caller
   supplies; the core stays provider- and host-agnostic.
2. **Mirror the reference when one exists.** Upstream `managed_agents`, its
   step serialization and its callback surfaces are the tie-breaker for names
   and semantics, so the port stays legible.
3. **Stay isomorphic.** Core stays browser-safe; a Node-only piece hides behind
   a subpath export, the way the MCP stdio transport already does.
4. **Ship a seam with one real implementation and a test**, never a config flag
   for a value that never changes and never an abstraction with one implementer.

## Phases

Each phase is one milestone. Milestone IDs S7–S11 are proposed for
`docs/01-project.md`; they are recorded there only once the owner approves.

### Phase 1 — S7: multi-agent orchestration

- **Deliverable:** `managed_agents` — a child agent exposed to the model as a
  callable tool — so a supervisor delegates a subtask that runs inside the
  child's own step budget.
- **Files:** `packages/core/src/agent/managed-agent.ts` and the core prompt,
  registry and agent files it touches, plus `packages/core/test/managed-agent.test.ts`.
- **Exit criterion:** a parent agent delegates to a child and folds the child's
  report back as an observation.
- **Status:** landed on 2026-10-16 — `managedAgent()` wraps a child as a
  tool, `AgentOptions.managedAgents` folds it into the manager's tool set, and the
  prompt renders it in a "team members" section apart from the tool list. Verified
  by eight core tests, a scripted end-to-end delegation run in `examples/vite-app`
  through the real QuickJS executor, and `pnpm gate`.

### Phase 2 — S8: durable runs and human-in-the-loop

- **Deliverable:** a run serializes its step state to a store seam and can
  resume from it; an approval/interrupt seam pauses a step for a human decision.
- **Files:** `packages/core/src/agent/**` and a `session`/`store` seam module.
- **Exit criterion:** a run stopped mid-loop round-trips through the store and
  continues; a gated tool call waits for an approval before it runs.
- **Verification:** a resume test over a serialized run; an approval test.
- **Status:** landed on 2026-10-16 — a step serializes to plain JSON
  (`stepToJSON`/`stepFromJSON`), `AgentMemory.toJSON`/`restore` and a `RunStore`
  seam with a `MemoryRunStore` checkpoint a run, and `run(task, { reset, checkpoint })`
  resumes from one; `AgentOptions.approve` gates every tool call at the registry
  seam both agent flavours route through. Verified by six core tests (a resume
  round-trip and the approval gate) and `pnpm gate`.

### Phase 3 — S9: observability and evaluation

- **Deliverable:** a trace exporter that consumes `AgentEvent` (an OTel-shaped
  interface, no hard dependency), and a small eval harness that scores a golden
  transcript.
- **Files:** `packages/core/src/**` exporter seam + `packages/core/test/**`.
- **Exit criterion:** one run produces a trace and one eval scores it against a
  fixture.
- **Verification:** an exporter test on a recorded stream; an eval test on a
  golden file.
- **Status:** landed on 2026-10-16 — `buildTrace` folds an `AgentEvent`
  stream into one OTel-shaped `TraceSpan` tree (a `run` root with a child span
  per step, planning pass and tool call, an injected clock for determinism), and
  `scoreRun` checks a completed run against a transcript's output, state,
  action-step count and event-type sequence. Both are exercised over the
  existing `fibonacci` golden fixture in one recorded run. Verified by four core
  tests and `pnpm gate`.

### Phase 4 — S10: persistent sessions and memory

- **Deliverable:** a session that persists across runs behind the store seam,
  and a run that can read prior turns.
- **Files:** `packages/core/src/**` session module.
- **Exit criterion:** a second run sees the first run's memory through a store.
- **Verification:** a two-run test over an in-memory store.
- **Status:** landed on 2026-10-16 — `AgentSession` takes a `checkpoint` option
  and threads it (with `reset:false`) into each `send`, so a turn continues the
  agent's prior memory and a new session naming the same checkpoint, over the
  same `RunStore`, reads the earlier turns. Verified by two core tests (a second
  session sees the first's task; no checkpoint means a fresh turn) and `pnpm gate`.
  The session snapshot itself is not yet rehydrated from the store — only the
  agent's memory is.

### Phase 5 — S11: guardrails and structured output

- **Deliverable:** a guardrail seam with tripwires on input/output, and a
  schema-bound final answer.
- **Files:** `packages/core/src/**` guardrail + output-schema modules.
- **Exit criterion:** a tripwire halts a run with a typed reason; a final answer
  is validated against a caller-supplied schema.
- **Verification:** a tripwire test; a schema-validation test.
- **Status:** landed on 2026-10-16 — `AgentOptions.guardrails` holds an `input`
  and an `output` tripwire, and `AgentOptions.outputSchema` a caller-supplied zod
  schema; a tripped wire or a schema mismatch fails the run with an
  `AgentGuardrailError` (new code `AGENT_GUARDRAIL`) before the terminal
  `run.completed` is emitted, and a passing schema reports its validated value.
  Verified by five core tests (input halt, input pass, output halt, schema
  reject, schema accept-and-coerce) and `pnpm gate`. One shared `complete()`
  choke point serves both completion paths (code-agent final call and
  tool-calling final answer).

**Later candidates** (not scheduled; from the research): provider router /
fallback and local runtimes, streaming UI transport, MCP server authoring,
multimodal and hosted tools, RAG/connectors, A2A.

## Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Scope creep toward a platform | High | High | Non-goals above; each phase must pass the four approach tests before it starts. |
| Resume/session semantics drift from upstream | Medium | Medium | Mirror the reference's step serialization; a divergence becomes a decision record. |
| Core stops being browser-safe as Node features appear | Medium | High | A test enforces that only subpath entries name a Node builtin. |
| A phase ships an abstraction with one implementer | Medium | Medium | One implementation plus a test; a second is added when a user asks. |

## Rollback

Each phase is additive behind a seam, so a phase that stalls is dropped without
touching the others; a landed seam that proves wrong is removed in one package
with no published dependents until the first release.

## Open questions

on 2026-10-16 (decision 0018), so multi-agent (S7) is the first phase and the
