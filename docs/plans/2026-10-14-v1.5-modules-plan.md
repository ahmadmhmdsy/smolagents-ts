# v1.5 modules — Implementation Plan

## Contract

- **Role:** the implementation plan for the v1.5 module sequence that T-13 owns,
  starting from the CLI package this session delivers.
- **Mutability:** once execution starts the steps below are frozen: a step that
  turned out wrong gets a note under the task that owns it, and the step's own
  text is not rewritten. Measured results are appended at the end.
- **Read when:** executing a v1.5 module, or reviewing what the sequence was
  supposed to deliver.
- **Update when:** a task's measured result differs from its prediction, or a
  task is added or dropped.

**Goal:** ship the six modules the design record's S6 row defers to v1.5 — a
Node CLI, the docs site with the React example's host, an MCP client, a Pyodide
executor, the remote executors and the L4/L5 UI layers — each as its own
package or app, with the CLI landing first because the owner named it first.

**Architecture:** every module here is additive. The v1 core, models, tools,
exec-quickjs and react packages keep their present surfaces, and the facade
re-exports what already exists. The CLI is the first new consumer of those
surfaces: it is Node-only, so the isomorphism rule that binds the core does not
bind it, and it carries no third-party runtime dependency. It drives the same
CodeAgent loop every other consumer drives, and it renders that loop's event
stream. The later modules follow the same shape: MCP and exec-pyodide arrive as
packages beside the existing five, the docs site and the example host as an app,
and the remote executors as adapters behind the core's CodeExecutor seam.

**Tech Stack:** pnpm 12.3.4 workspaces, TypeScript 6, tsup 8.5.1 (ESM only),
vitest 5, the existing pack smoke, and for this package Node's own
`readline/promises`, `process` and `util` modules rather than a CLI framework.

**Spec:** design section 14 (the S6 row), design section 10.3 (the deferred
packages), T-13 in `docs/04-tasks.md`, and the CLI port's upstream source pinned
at 1.27.0.dev0.

**Depends on:** S0 to S6 and S1.5, all done or reached.

**Dependency order:** Task 1 is free to land now. Task 2 waits on Task 1 only
for the repository's shape, not for code. Tasks 3 to 6 are independent of one
another and of Task 2.

**Task ownership:** one writer at a time. Task 1 owns `packages/cli/**`, the
root router row and the CLI's rule file. Each later task owns the package or app
it creates; no two tasks in this plan share a file.

## Tasks

### Task 1: the CLI package

**Files:**
- Create: `packages/cli/package.json`, `tsup.config.ts`, `tsconfig.json`, `tsconfig.test.json`, `vitest.config.ts`
- Create: the package's `src/` modules (arguments, errors, model factory, tool factory, renderer, terminal, interactive setup, run function, bin) and its `test/` files
- Create: `packages/cli/AGENTS.md`, the CLI's rule file under `rules/components/`, the changeset
- Modify: `AGENTS.md`, `scripts/pack-smoke.mjs`, `docs/01-project.md`, `docs/04-tasks.md`

- [ ] **Step 1: write the plan first**
This plan, before any package file exists, so the deliverable list is
pre-registered rather than reconstructed from the code.

- [ ] **Step 2: port the argument surface**
The positional prompt, the eight flags upstream's parser declares, a
`--help` that exits 0, and a usage error that exits 2. The parser is
hand-rolled because upstream's `--imports` and `--tools` take a
space-separated list, which `node:util`'s `parseArgs` does not model.

- [ ] **Step 3: port the factories**
Upstream's `load_model` maps onto this port's adapters: `InferenceClientModel`
becomes `HuggingFaceModel` and `OpenAIModel` becomes `OpenAICompatibleModel`.
The two upstream types with no adapter here are refused by name with a typed
error, and the tool factory maps `web_search` and `visit_webpage` onto the
tools package's defaults while refusing `python_interpreter` by name.

- [ ] **Step 4: port interactive mode and the renderer**
The configuration prompts, the tool table, the model questions, the
advanced-options branch and the default task prompt, all behind an injected
prompter so a test never reads a terminal. The renderer turns the core's
`AgentEvent` union into text at three verbosity levels, with ANSI codes used
only when the output is a terminal.

- [ ] **Step 5: wire the run function and the bin**
The run function builds the model, the tools and the agent, drains
`agent.stream`, renders every event and resolves an exit code. The bin
parses the process's arguments and delegates.

- [ ] **Step 6: test**
Unit tests for the parser, each factory and the renderer, plus one end-to-end
run through the real `CodeAgent` with the core's `MockModel` and
`ScriptedExecutor`, asserting the exit code and the rendered text.

- [ ] **Step 7: pack integration**
The router row, the scoped entry, the component rule, the changeset and the
pack smoke's installed-bin execution.

- [ ] **Step 8: verify**
Run the build, the package's test project, typecheck, lint, depcruise and the
context validator; append the measured results here.

### Task 2: the docs site and the React example host

**Deliverable:** an app that publishes the numbered documents and hosts the
runnable React example T-12 owns. The site generator and the example's host are
one decision because T-12 and this plan's spec row both wait on it.

**Open question:** whether the site is a static generator over `docs/` or a
hand-maintained app, and whether the example renders inside it or beside it.
The owner answers before this task starts.

**Verification:** the site builds offline and the example runs against the
published facade without a provider key.

### Task 3: the MCP client package

**Deliverable:** an MCP client behind the core's tool seam, so a remote MCP
server's tools appear to an agent as ordinary tools. The upstream module is
`mcp_client.py`, deferred at design line 942.

**Open question:** the transport set for the first release, and whether the
client is a peer dependency of the models layer or a package of its own.

**Verification:** a client driven against a recorded transport fixture, with no
live server in the gate.

### Task 4: exec-pyodide

**Deliverable:** a `CodeExecutor` that runs Python in Pyodide, the fidelity
option the design's fallback ladder names. It ships as a package beside
`exec-quickjs` and implements the same interface.

**Open question:** the Pyodide load path and bundle size, and whether the first
release supports only the browser target or Node too.

**Verification:** the executor's own suite under its vitest project, plus the
pack smoke's import check.

### Task 5: the remote executors

**Deliverable:** the Docker, E2B and process executors behind the same
`CodeExecutor` seam, each in its own package or subpath so a browser consumer
never pulls a container client. Upstream's `remote_executors.py` is the source.

**Open question:** which backends ship first, and how a backend test runs
offline when the backend is a daemon or a hosted sandbox.

**Verification:** each executor's suite against an injected transport double,
one per backend, with the live path left to a runbook.

### Task 6: L4 and L5

**Deliverable:** the styled pattern layer and the styled component layer over
the existing L3 primitives in `packages/react`. L4 composes the primitives into
patterns; L5 ships the styled components those patterns need.

**Open question:** whether the styled layer is a new package or a subpath of the
React package, and which stylesheet strategy it commits to.

**Verification:** the React package's suite grows with the layers and the
existing accessibility assertions stay green.

## Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| V15-R1 | the CLI's model factory hides an absent adapter behind a default | medium | high | every unsupported model type raises a typed error that names the alternatives |
| V15-R2 | the docs site makes the numbered documents a second home for facts | medium | high | the site renders what the documents already say; no page restates a fact |
| V15-R3 | a remote executor makes the gate depend on a daemon | medium | high | each backend's tests drive an injected double, and the live path is documented instead of gated |
| V15-R4 | the Pyodide bundle dwarfs the QuickJS one | high | medium | the executor is a separate package, so the core and the default executor are unaffected |
| V15-R5 | L4/L5 arrives before the L3 surface is stable | low | medium | the layers compose the published barrel only; a gap in it is a core change, not a layer change |

## Rollback

Every task is additive. Deleting the package or app a task created, its router
row when it has one, and its rule file returns the tree to the state before it,
and removing the changeset keeps the release untouched. No task here rewrites an
existing package's surface, so a rollback never has to unmake a semantic change.

## Open questions

1. **The first module after the CLI.** T-13's gate names the docs site with the
   example host next, then MCP, exec-pyodide, remote executors and L4/L5. The
   owner confirms that order before Task 2 starts.
2. **The docs site's engine.** Task 2's deliverable is fixed; the generator is
   not. The owner picks it with T-12's host.
3. **The remote backends' order.** Task 5 names three backends and no sequence.
4. **Whether L4/L5 is one task or two.** This plan keeps them together; the

## Notes

- Task 1's step list is the only one written at step granularity. The later
  tasks are roadmap rows: they fix a deliverable and a verification, and the
  session that starts one writes its own plan in this directory.
- The CLI's manifest keeps the tools package's fields and adds a `bin` plus an
  optional peer for the executor package, which is the one field the CLI needs
  and the tools package does not.
- Upstream's `cli.py` parses a verbosity level and never reads it; this port
  wires it to the renderer, and the divergence is recorded in the measured
  results.

Step 8 predicted that the packed bin would need the executor only as an optional
peer. Measurement corrected that: `pnpm pack` refuses a `workspace:*` peer that
is not installed, reporting `ERR_PNPM_CANNOT_RESOLVE_WORKSPACE_PROTOCOL`, so the
same range is declared a second time as a `devDependency`. The link makes the
peer resolvable while packing, and `dependencies` still holds exactly the three
workspace packages. A throwaway consumer that installed the packed `core`,
`models`, `tools` and `cli` tarballs ran the installed bin with `--help` and
read its usage line.

Four upstream disagreements were decided here, recorded so a reader does not
rediscover them one at a time. Upstream parses `--verbosity-level` and never
reads the value, while this port passes it to the renderer. The interactive menu
offers a server model that upstream's own loader cannot build, and it resets the
prompted action type to code; this port keeps both behaviours. The environment
variables are named `HF_TOKEN` and `OPENAI_API_KEY`, and the interactive key
question becomes a note naming the variable, so no credential is typed into a
terminal that echoes it. The docstring count mismatch against the design record
is left as the design wrote it.
